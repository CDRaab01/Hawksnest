# Hawksnest audit — August 2026

**Date:** 2026-08-02 · **Weighting:** Android usage is the primary target; web and deploy are
audited insofar as they affect it.

---

## 1. Scope and method

| Surface | What was inspected |
|---|---|
| Hawksnest repo | `origin/main` @ `0e334e6` (PR #108 merged). 185 web files, 230 Kotlin files (169 main / 56 unit test / 3 instrumented / 2 Sift), all docs, all 4 workflows. |
| Live Kubernetes | Read-only, via `wsl -d Dragonfly -u root -- kubectl`. Pods, images, resources, PVCs, probes, events, logs since pod start (45 h). |
| Live Home Assistant | Read-only `kubectl exec` into `deploy/home-assistant`: `/config/automations.yaml`, `/config/configuration.yaml`, HA's own error log. |
| `hawksnest-automation` | Repo @ `a4509c6`, clean tree. Kustomize base + `prod`/`staging` overlays, 4 workflows, `windows/` glue scripts. |

**Not inspected.** No on-device run (no phone attached to this session), no HA UI walkthrough, no
Frigate UI, no camera live-path exercise. Every finding below is from source, manifests, or live
read-only queries — where a finding *needs* a device to confirm, it says so.

**A note on freshness.** Two error classes that looked severe in the raw log tallies turned out to
have **stopped** on 2026-08-01 (see §3). Log counts alone would have overstated them; the audit
uses last-occurrence timestamps, not totals. That matters because the fixes were made by hand on
the live instance and are **not in git** — which is itself the more important finding.

## 2. Verdict

The engineering is good and the record-keeping is not. The Android app is the more capable of the
two clients — richer controls, six home-screen widgets, an RTSP tier the web physically cannot
have — and its hard parts (offline grace, the camera transport ladder, widget freshness) are
carefully thought through and unit-tested. What is missing is everything *around* the code:
**zero ViewModel tests and zero Compose behaviour tests**, no on-device verification of the two
features most likely to fail on-device (push, live camera), and a documentation set that
contradicts the shipped configuration in at least one security-relevant place. On the deployment
side the cluster is healthy — 11/11 pods running, no restarts, no OOMKills — but the live HA
config has drifted to **21 automations against 6 in the seed ConfigMap**, with the extra 15
existing only on an NFS volume that CI never sees.

Nothing here is on fire. Several things are load-bearing and unwitnessed.

### Against the suite 1.0 bar (`C:\Code\ROADMAP3.md`)

| # | Bar item | Hawksnest |
|---|---|---|
| 1 | Onboarding | ❌ None. First launch is a blank Settings form. |
| 2 | Designed empty / loading / error states | ✅ Skeletons throughout; offline is exemplary. |
| 3 | Motion + celebration, dark/light parity | ⚠️ Motion yes. Light colours exist but Android ships no way to select them. |
| 4 | Defined offline behavior | ✅ **The model for the suite.** 120 s grace, security states masked instantly, no persistent cache. |
| 5 | No dead settings | ⚠️ Settings is clean, but a dead *screen* exists (`CamerasScreen.kt`, §4.1). |
| 6 | Recorded on-device verification pass | ❌ Open since 2026-07-16. Both push and camera. |
| 7 | Roborazzi baselines gating, or job deleted | ⚠️ Sift runs and is baseline-gated, but `continue-on-error: true` means it gates nothing. |
| 8 | Proud icon + first-launch "What's new" | ❌ No what's-new card. |
| 9 | `versionName 1.0.0` set deliberately | ✅ ROADMAP3 names Hawksnest the model for this. |
| 10 | Truthful repo docs | ❌ **The worst category.** 12 stale claims across 6 files (§6). Partially fixed by this audit. |
| 11 | Accessibility (1.3× font, TalkBack) | ❌ No evidence either was ever run. |
| 12 | Biometric lock where data warrants | ✅ Considered and deliberately removed by the owner; documented. |

**4 pass, 3 partial, 5 fail.** Items 6, 7 and 10 are the ones blocking an honest 1.0 claim, and
10 is the only one that is purely a matter of sitting down and writing.

### What is genuinely good

Worth naming, so the criticism below is calibrated:

- **The offline model** (`core/logic/Offline.kt`, `src/lib/offline.ts`). A 120 s grace window where
  non-security entities stay visible but dimmed and labelled, while locks and the alarm are masked
  to `unavailable` *the instant* the socket drops. No persistent entity cache anywhere, ever. This
  is the correct answer to a genuinely hard problem and both platforms implement it identically.
- **Widget freshness policy** (`core/logic/WidgetModel.kt`, 894 lines, fully unit-tested).
  60 s expiry with `maskState` for lock/alarm, a 15-minute age label for light/temp, explicit
  `widgetIsOptimistic` / `widgetKeepsStaleReading` predicates. A home-screen widget showing a stale
  lock state is a real safety problem and this file takes it seriously.
- **The camera transport ladder decides once per camera.** Not per frame, not per reconnect — so
  transport cannot flap mid-session. And HLS resolution is *lazy*, because `camera/stream` wakes a
  battery camera's pipeline. That is a subtle, hardware-informed decision.
- **`OPENAI_BASE_URL` is declared `optional: false`** in the Frigate manifest. A missing key fails
  the container rather than silently shipping interior-camera snapshots to `api.openai.com`.
  Fail-closed on the exact axis that matters.
- **`android-release.yml` verifies the built APK's signer against the pinned suite SHA-256** and
  fails on mismatch. A missing keystore secret cannot silently publish an uninstallable APK.

## 3. Findings — live HA deployment

### 3.1 HIGH — Frigate GenAI has been failing continuously, and nothing notices

```
frigate.genai.openai WARNING : OpenAI returned an error: Error code: 400 -
  {'error': 'Model does not support images. Please use a model that does.'}
```

Confirmed firing **as of 17:20 today**, roughly every 20–40 seconds. The model configured behind
`OPENAI_BASE_URL` (LM Studio on the Windows host) has no vision capability, so **every AI event
description and every semantic-search enrichment silently fails**. This is the feature that feeds
`EventDescription` in both clients and the camera-object push notification text.

It is a warning, not an error, so it never surfaces. The existing
`hawksnest_frigate_detection_watchdog` automation only checks `switch.*_detect` and
`sensor.*_camera_fps` — it has no notion of GenAI health.

**Fix:** load a vision-capable model in LM Studio (a Qwen2.5-VL or similar), or set
`genai.enabled: false` in the Frigate config until one is loaded. Then extend the watchdog to
alert on GenAI failure so this cannot recur unobserved.

### 3.2 HIGH — Duplicate automation ID on the doorbell push path

`/config/automations.yaml` declares `- id: hawksnest_push_doorbell` **twice**, at line 29 and line
57, with different aliases and different schema generations:

```yaml
29: - id: hawksnest_push_doorbell
30:   alias: 'Hawksnest push: doorbell ding'      # the seeded one, legacy `trigger:` key
...
57: - id: hawksnest_push_doorbell
58:   alias: doorbell                              # UI-created, modern `triggers:` key
```

HA is explicit about the consequence:

```
ERROR [homeassistant.components.automation] Platform automation does not generate unique IDs.
  ID hawksnest_push_doorbell already exists - ignoring automation.doorbell
```

So the second one — hand-built in the HA UI — **has never run and never will**. Whoever created it
believes they configured a doorbell notification. On the doorbell path specifically, a silently
dead automation is the worst place for this to be.

**Fix:** decide which one is wanted, delete the other, keep the winner's ID. If the UI one is the
intended behaviour, give it a distinct ID and remove the seed copy from the live file (and then
reconcile the seed — see 3.5).

### 3.3 MEDIUM — Two large error classes stopped on 2026-08-01, and the fixes exist only on the PVC

Raw log tallies since pod start (45 h) look alarming:

| Count | Message |
|---|---|
| 2,068 | `Template variable warning: 'ReadOnlyDict object' has no attribute 'event_type'` — the ZEN32 preset automations |
| 1,686 | `nursery_led_effect_alarm_too_hot: No zwave_js nodes found for given targets` (1,124 + 562) |
| 569 | `Device 83fde5fed357870364f7dc7b9c127ac5 config entry is not loaded` |

They are not currently firing. The template warnings ran at a steady **160/hour** from 07-31 21:00
and stopped at **2026-08-01 11:39**; the nursery errors stopped in the same minute. Reading the
live automation's own description confirms why — it was rewritten by hand:

> *"TEMPERATURE SOURCE CHANGED 2026-08-02, from the ZSE44 to the switch's OWN sensor… on 2026-08-01
> the switch read 72.6F against the ZSE44's 72.2F…"*

So these were real, they were found, and they were fixed well — the reasoning in that description
is better than most commit messages. **The problem is that none of it is in git.** The fix lives on
`/config/automations.yaml` on the NFS PVC. A PVC restore, a re-seed, or a new cluster loses it.

**Residual risk worth fixing anyway:** the automation targets `device_id:
83fde5fed357870364f7dc7b9c127ac5` directly. Device IDs are registry-local and change on re-pair, so
this will break silently again the next time that Z-Wave node is re-included. Prefer an
`entity_id` target, or accept the coupling and note it.

### 3.4 MEDIUM — Frigate is at 93% of its memory limit

`frigate` is using **4,764 Mi against a 5 Gi limit** with 7 cameras at 5 fps each, 83 GB of
recordings, and `semantic_search` running a jinav2 index. One more camera, a reindex, or a
recording backlog OOMKills the NVR.

Frigate deliberately has **no liveness probe** (documented, correct — it avoids an inescapable
kill-loop on slow camera init), which means recovery from an OOM depends on the kubelet restart
alone and there is no alert on the way down.

**Fix:** raise the limit to 6–7 Gi (the node is at 16 GB / 66% of 24 GB, there is headroom), and add
a memory alert. Do not add a liveness probe — the existing reasoning for omitting it is sound.

### 3.5 MEDIUM — Live HA config has drifted far from the seed, and only the *lower*-value config is drift-guarded

| | Seed ConfigMap | Live on PVC |
|---|---|---|
| `automations.yaml` | 6 automations, ~410 lines | **21 automations, 880 lines** |
| `scripts.yaml` | `{}` | `master_bedroom_strip_power_up` |
| `configuration.yaml` `trusted_proxies` | includes pod CIDR `10.42.0.0/16` | **omits it** |

The 15 extra automations — Cooper's and Master Bedroom ZEN32 scene control, the WLED nursery and
bedroom LED-bar stacks, All Lock, Garage Door Unarm — represent most of the actual home automation
in this house, and they exist in exactly one place: an NFS volume. They never pass through CI's
`ha-config-check` job, which validates only the seed.

The irony is that `hawksnest-automation` **already has a drift workflow** — `frigate-drift.yml`,
which diffs live Frigate config against the seed on a schedule. That mechanism is pointed at the
config with fewer hand edits and lower blast radius, while the automations that control three
deadbolts and a baby's room are unguarded.

The missing `10.42.0.0/16` from live `trusted_proxies` is benign *today* only because
`deploy/nginx.conf` clears `X-Forwarded-For` on all five HA-proxied locations. It removes the
documented belt-and-braces alternative, so if anyone ever "simplifies" the nginx config, camera
frames break again exactly as they did before.

**Fix:** clone `frigate-drift.yml` into `ha-config-drift.yml` covering `automations.yaml`,
`scripts.yaml`, `scenes.yaml`, `configuration.yaml`. Then do a one-time reconciliation: pull the
live file into the seed ConfigMap so git becomes the source of truth again.

### 3.6 MEDIUM — `zwave-js-ui` is the least-protected pod and owns the door locks

The one pod that owns the Z-Wave radio for three Schlage deadbolts runs with:

- image tag **`:latest`** — rolls forward on any pod recreate, unpinned, on the lock stack;
- `privileged: true` (needed for the USB serial device, but total);
- **no liveness probe and no readiness probe at all.**

Frigate and ring-mqtt each omit a liveness probe *deliberately*, with a comment explaining why.
`zwave-js-ui` has no probes because nobody added any — it is absence, not a decision. A wedged
Z-Wave daemon keeps its Service endpoint and HA keeps seeing the websocket as up.

**Fix:** pin the tag to the running version (11.22.0). Add a readiness probe on the websocket port.
Leave liveness off if the same slow-init reasoning applies, but write down that it is a choice.

### 3.7 MEDIUM — `home-assistant:stable` is unpinned

Currently 2026.6.4. Any pod recreate can pull a new minor with breaking config changes, on the
stack that controls three deadbolts and an alarm panel. The Frigate manifest carries an excellent
comment explaining exactly why *it* refuses to float; HA does not follow its own house rule.

### 3.8 LOW

- **No Ingress despite a working Traefik LoadBalancer** at `192.168.4.34`. Everything rides
  NodePorts plus host-side socat/Tailscale Serve. `hawksnest-automation/CLAUDE.md` already calls
  this "the known fragile link."
- **Reolink integration loses cameras intermittently** — Garage 502, Kitchen/Big Room/Stairway
  connection-refused on :80, clustered around 02:00. Frigate's RTSP path is unaffected, so this
  only breaks the switch/privacy-mode entities — including `switch.bedroom_privacy_mode`, the
  hardware half of the bedroom privacy window.
- **Bedroom ffmpeg watchdog restarts outside the privacy window** (observed 12:05, midday), with
  continuous `Non-monotonic DTS` on `bedroom.detect`. Commit `a4509c6` fixed the privacy-window
  crash-loop; this is a separate, genuine camera/network problem.
- **Staging `ring-mqtt` is permanently 0/1** (no Ring refresh token in the staging PVC), emitting a
  readiness event every few seconds. Cosmetic, but it is the only red line in `get pods` and will
  mask a real staging failure.
- **Secret rotation has no rollout trigger.** `disableNameSuffixHash: true` means editing a secret
  is a silent no-op until someone remembers `rollout restart`. Documented, still a trap.
- **S2 Z-Wave security keys are still not in a password manager** (`PROGRESS.md` admits it), and
  Z-Wave **user code slots were never set** (slot 1 Christian / slot 2 Elizabeth) — the one genuinely
  outstanding item on that repo's acceptance checklist.
- **`PROGRESS.md` is five weeks stale**, listing as "pending" three things that are live.

## 4. Findings — Android

### 4.1 Dead screen and dead route

`ui/cameras/CamerasScreen.kt` is a Phase 0 placeholder — *"Camera snapshots will appear here once
Home Assistant is connected"* — and is **referenced by no file in the app**. `Screen.Cameras` is
declared in `ui/navigation/Screen.kt` and registered in no `composable {}` block. Cameras fold into
Home instead. Verified: `grep -rn "CamerasScreen\|Screen.Cameras"` outside the file itself returns
nothing.

Suite 1.0 bar item #5 is "no dead settings"; the same principle applies to a screen that renders a
promise the app has already kept elsewhere. **Delete both.**

### 4.2 The Settings placeholder suggests a URL a release build will reject

`ui/settings/SettingsScreen.kt:115`:

```kotlin
placeholder = { Text("http://hawksnest.<tailnet>.ts.net:8080") },
```

`res/xml/network_security_config.xml` sets `cleartextTrafficPermitted="false"`. A release build
**cannot connect to that URL**, and the failure will present as a generic connection error with no
hint that the scheme is the problem. `android/README.md` correctly says to use
`https://<host>.ts.net:8443` — the in-app hint contradicts the README and the shipped policy.

Compounding it, `core/ha/HaSource.kt:524` defaults a bare host to **`ws://`**:

```kotlin
else -> "ws://$trimmed"
```

So a user who types `hawksnest.tail1234.ts.net:8443` — reasonable, given the placeholder shows a
bare-ish host — gets cleartext, which is then blocked. **Fix both:** placeholder to the `https://…:8443`
form, and default a schemeless host to `wss://`. If cleartext is ever genuinely wanted, make the
user type `ws://` explicitly.

### 4.3 Zero ViewModel tests, zero Compose behaviour tests

56 unit test classes cover `core/logic` (34 of 37 files), all of `core/ha`, all of `core/net`, and
the widget data layer. That is genuinely strong coverage of the *kernel*. Above it:

- **No ViewModel is tested.** Not `HomeViewModel`, `DevicesViewModel`, `EntityDetailViewModel`,
  `SettingsViewModel`, `AutomationEditViewModel`, and notably not `CameraPlayerViewModel` (365
  lines) whose `resolveRingClip` / `awaitRecordingUrl` timeout state machine the code comments
  themselves describe as subtle.
- **No Compose behaviour test exists** across ~60 composables. The only Robolectric render in the
  repo is the Sift *design-slop* suite, which checks visual heuristics, not behaviour. The gesture
  *math* is tested (`LightFeelTest`, `ThermostatTest`, `LockStateTest`); the wiring from a gesture to
  a service call is not. Nothing proves that dragging `LightPillar` calls `dimCommit`, that
  `SlideToAct` requires a full traverse, or that `RockerSwitch` sends the right direction — the
  latter being the exact bug fixed in PR #108.
- **The camera ladder's step-down is untested.** `CameraPlayer.kt` (784 lines) holds the tri-state
  `canGo2rtc` / `wantsHls` interlock that the docs call load-bearing: while the go2rtc stream list
  is in flight, both WebRTC arms must hold *and* HLS must not resolve, because resolving HLS early
  wakes a battery camera's pipeline. No test walks
  `rtspFailed → go2rtc → go2rtcFailed → WebRTC → HLS`. `Go2rtcStreamsTest` and `RtspHealthTest`
  cover only the circuit breakers.

Ranked by risk: `CameraPlayerViewModel` first (most intricate, hardware-coupled, hardest to
reproduce by hand), then the ladder interlock, then Compose tests for the five premium controls.

### 4.4 The instrumented suite is three tests against a mock that supports far more

`app/src/androidTest` holds `MockHaInstrumentedTest`, `MockControl`, and `TokenCipherTest`. The
mock-ha `/__scenario` API supports `disconnect`, `service-outcome` (`confirm|jammed|reject|silent`),
`stream-outcome`, and four scenarios including `lock-jam` and `bad-token`.

The **web** Playwright suite uses all of that — `lock-pending.spec.ts` alone has 5 tests covering
pending/jam/rejected. The Android suite, against the same fake backend, covers none of it. Lock
slide, offline/grace transitions, doorbell deep-link tap, and camera open are all unexercised on the
platform where they actually get used.

Worse, **no workflow runs the instrumented suite at all.** `scripts/android-emulator-test.sh` exists
and needs KVM; nothing invokes it. The cross-harness contract that mock-ha was built to serve is
half-unused.

### 4.5 Platform integrations that do not exist

Verified absent by exhaustive grep over `app/src`, `build.gradle.kts`, and the manifest:

| Absent | Note |
|---|---|
| App shortcuts | No `shortcuts.xml`, no `ShortcutManager`. Long-press the icon → nothing. |
| Quick Settings tiles | No `TileService`. |
| Personalization editor | Web has `/customize` (dnd-kit reorder, pin, hide). `util/DevicePrefsStore.kt` persists only `hidden_entities` and `entity_renames` — **no pin, no order**. `config/Favorites.kt:5` still promises "the Phase 2 personalization editor lets the user pin/unpin and reorder." It was never built. |
| Theme picker | `ui/theme/Theme.kt:69` takes `darkTheme: Boolean = isSystemInDarkTheme()`. `LightColors` and `lightPulseColors()` both exist. Only the control is missing. |
| Picture-in-Picture | Camera player has fullscreen but no `PictureInPictureParams`. |
| Notification quick-actions | No `RemoteInput`, no action buttons. A doorbell notification can only be tapped. |
| Widget previews / themed icons | No API 31+ `previewLayout`, no monochrome icon layer. |
| Crash reporting | None on either platform. ROADMAP2 T1 #7. |
| Onboarding, what's-new | Neither. Suite 1.0 bar #1 and #8. |
| Wear OS, Android Auto, NFC, geofencing, WorkManager, biometrics | All absent. **All correctly absent** — see §7.3. |

### 4.6 Backup-exclusion is path-based and will silently rot

`res/xml/data_extraction_rules.xml` and `backup_rules.xml` exclude
`datastore/hawksnest_prefs.preferences_pb` **by path**. Today that file holds the Keystore-wrapped
HA token *and* the RTSP camera password, so the exclusion is correct. The moment anyone adds a
second DataStore for anything sensitive, it is backed up to the cloud by default and nobody will
notice. The class comment flags the hazard; nothing enforces it.

**Fix:** a unit test asserting that every `preferencesDataStore(name = …)` declared in the source
tree appears in both XML rule files. Cheap, and it makes the invariant self-defending.

### 4.7 Smaller items

- **`isMinifyEnabled = false`** in release. ProGuard rules exist and are never exercised, so they
  are unverified the day minification is turned on.
- **PRs #83 and #105 are overlapping fixes for the same widget-wedging bug** ("recover instances
  wedged by the previous update" / "rebuild every instance once on app start"). One should be
  closed before either merges.
- **`push/` runtime is entirely unverified.** `NtfyPushService`, `PushNotifier`, `BootReceiver`,
  `WidgetLiveBridge`, `PushNav` have no tests; only the pure `NtfyMessage` and `PushRoute` do. The
  README has said "push on-device verify pending" since Phase 4.

## 5. Findings — web, deploy, CI

- **`deploy.yml` deploys on push to `main` without gating on `ci.yml`.** A red typecheck, test, e2e
  or kubeconform does not stop the rollout — they race. Convert to `workflow_run` after CI success,
  matching the pattern the rest of the suite uses.
- **`deploy.test.ts` — the self-declared spec for deploy changes — never asserts the `/go2rtc/`
  location.** `/ring-timeline/` is asserted; `/go2rtc/` (0 matches) is not, despite being the route
  the entire top live-video tier and two-way Talk depend on. Also unasserted: resource limits,
  replica count, probe paths, the `map $http_upgrade` block, `imagePullPolicy`.
- **Sift is fine, and three docs say otherwise.** `V1.md`, `ROADMAP.md` and an earlier draft of this
  audit all describe the `sift-audit` job as permanently red on an AGP 8.5.0 vs 9.1.1 mismatch. It
  is not: Sift was bumped to 9.1.1 in its own PR #2, and the job has been green since — verified on
  run `30712842185`, where the composite build resolves and `HawksnestDesignSlopTest` actually runs.
  The remaining question is a different and smaller one: `continue-on-error: true` means the audit
  reports but gates nothing, so 1.0 bar item #7 ("baselines gating, or job deleted") is still not
  satisfied. Decide whether to make it gating now that it works.
  <br>*Method note: this claim was inherited from the docs rather than checked against CI, and it
  was wrong. Worth remembering that a stale doc is an unreliable source even when three of them
  agree.*
- **Two version schemes in one repo.** `android-ci.yml`'s `android-release` job hardcodes
  `VERSION_NAME: 0.1.${run_number}` while `android-release.yml` derives `1.0.x`.
- **No mock-ha Frigate scenario.** The four scenarios are default / lock-jam / bad-token /
  ring-camera. Frigate's WS commands (`frigate/events/get`, `frigate/recordings/get`,
  `auth/sign_path`) are mocked only at the vitest level. The bug class that bit twice — *"the REST
  route never existed and the test stubbed the nonexistent route"* — is exactly what an e2e Frigate
  scenario would catch.
- **No live camera coverage anywhere**, by construction: the mock serves no `web_rtc` camera. The
  manual `docs/CAMERA-SMOKE.md` checklist is the only gate, it has never been formally run, and it
  contains an unanswered question of its own (PTZ continuous-vs-step).
- **Web `switch` has no card** — it falls through to the read-only `GenericCard` while Android has
  a first-class `RockerSwitch`. A rare case of Android being ahead.
- **Hygiene:** ~20 dead `claude/*` remote branches from 2026-06-25→07-01; four dependabot PRs
  backed up (#77 open since 2026-07-18); PR #17 stale since 2026-06-27 that `V1.md` itself says to
  close.
- **Known and accepted, but untracked:** web token in localStorage until OAuth; native-HLS/Safari
  401s on Frigate VOD segments; `FRIGATE_RETENTION_DAYS` a hand-synced constant; Frigate gap
  knowledge unnormalized so scrubbing into a recording gap 404s; Frigate VOD's ~3 h
  nginx-vod-module ceiling. None of these appear on any roadmap.

## 7. Android feature shortlist

Ranked by (value to daily use) ÷ (effort), against gaps this audit actually found. **S** ≈ an
afternoon, **M** ≈ a few days, **L** ≈ a week-plus.

### 7.1 Do these

| 11 | Widget `previewLayout` + monochrome themed icon | Six widgets and the picker shows static images; themed icons are table stakes on Android 13+. | S |

### 7.3 Considered and not recommended

- **Wear OS** — a watch tile for "lock the door" is appealing, but it is a second app, a second
  release train, and a second signing story for one gesture that a QS tile (#4) delivers for a
  fraction of the cost. Revisit only if a watch enters the household.
- **Android Auto** — no meaningful use case. Nothing in this app should be operated while driving.
- **NFC tags** — genuinely useful in some HA setups ("tap to arm on the way out"), but it duplicates
  the ZEN32 wall pads that already exist at every relevant door.
- **Geofencing / presence** — deliberately deferred in `hawksnest-automation/README.md`
  ("presence auto-lock"). Presence belongs in HA, not the client; the app should read it, not
  compute it.
- **WorkManager background refresh** — the current design is foreground-and-event-driven on purpose,
  and `WidgetLiveBridge` already covers the live case. Background polling would add battery cost
  and a stale-security-state hazard for no user-visible gain.
- **FCM push** — already rejected. ntfy is self-hosted, tailnet-only, and Google-free; that is the
  right posture for a house.
