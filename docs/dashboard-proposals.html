Android · Home

The landing screen, before and after

Today the Home screen is three things: arm discs, camera wall, one Rooms row. It's clean, but the top third spends 200 dp saying one sentence, and the favourites we already let people pin never appear here.

The proposed screen swaps the prose line for counts, then adds pinned favourites and a chip row of household activity below it — still camera-forward, still one scroll.

The two additions are kept strictly disjoint: the counts card owns security posture, the chips own everything that isn't security. A chip that said “2 doors open” would just be restating 4/6 closed one card higher up.

Both platforms · card scale

Why the prose line has to go

SecurityStatusBar.tsx:79 builds its summary by joining every offender with ·. One offender reads beautifully. Five wrap to three lines and stop being glanceable — and it's five exactly when you most need to glance.

Counts with denominators hold their size no matter how bad it gets. We already compute all four buckets in that same useMemo.

The offenders aren't lost — they move one tap deeper, which is where the prose belongs.

note on the score Material Clean's headline “62/100” is skipped on purpose: a single number can't represent an entity whose state we've masked. Offline must subtract, never be silently dropped from the denominator.
Web · ≥1024px

A desktop layout, because we ship a browser app

We serve from an nginx pod, so people open Hawksnest on a laptop — and get a phone screen stretched to 2560px. There are 13 responsive breakpoint usages in all of src/.

The fix is cheap because the information architecture is already right: the sidebar is BottomBar's exact five routes, re-laid-out at lg:. Same components, two columns, four camera tiles instead of two.

Both platforms · new cards

Weather, and climate with its own history

weather isn't in the domain map at cards.ts:16-25, so a weather entity renders as GenericCard today — a label and a raw state string.

Climate has a card, but no trend. Sparkline.tsx already exists and HistoryScreen already fetches the series, so the setpoint card is mostly assembly.

The segmented mode pill replaces a row of buttons and is the same control the alarm could use on desktop, where three 64px discs are more thumb than a mouse needs.

What each one costs

ChangeSizeWhereWhy it's cheap (or isn't)
Security counts S SecurityStatusBar.tsx All four buckets are already computed in the existing useMemo — this is a render change, not a logic change.
Favourites on Home S DashboardScreen.tsx config/favorites.ts, prefsStore and the Customize editor all exist. Nothing renders them on the landing screen.
Activity chip row M new StatusChips.tsx Derived client-side from the entity store — Material Clean needs template sensors and a Spook dependency for the same numbers. Scoped to non-security domains so it never restates the counts card.
Weather card M cards.ts + new card New domain, new card, plus condition→backdrop mapping. Android needs its own Compose version.
Climate sparkline M ClimateCard.tsx Sparkline.tsx exists; wiring the history fetch into a card that doesn't currently fetch is the real work.
Desktop sidebar L BottomBar.tsx, screens Cheap to draw, broad to land — every screen needs a wide-viewport pass, and the E2E suite is written against mobile layout.

These are mockups, not screenshots — hand-built HTML using the real token values, not the React or Compose components rendering. Camera tiles are gradients standing in for WebRTC frames, and the weather values are invented because no weather entity is wired up yet. Treat the layouts as proposals to build against, not as a shipped build.
